# 接口文档

> 本文件是所有「代码设计实现文档」的接口对照基准。
> 状态：**已按 MVP 口径重写（feat-004，2026-09-26）**
> 实现：`api/index.js`（出口）→ `api/constants.js` / `api/errors.js` / `api/mock/*` / `api/http.js`
> 数据源：MVP 固定 mock（`USE_MOCK = true`），HTTP 路由已固定但未实现（`api/http.js` 抛 `NOT_IMPLEMENTED`）
> 规范来源：`.codebuddy/skills/api-design/SKILL.md`（RESTful、资源名词、`/api/v1`、camelCase、统一错误体、分页）

## 0. 调用约定

| 项 | 约定 |
|---|---|
| 页面引用方式 | `import { AttractionApi, GuideApi, OrderApi } from '@/api/index.js'`；**禁止**直接 import `api/mock/` |
| 数据源切换 | `api/index.js` 的 `USE_MOCK`；切后端时改这一处，页面代码不动 |
| 字段命名 | 接口一律 camelCase；DB 用 snake_case，映射见 `docx/database/数据库设计.md` 第 4 节 |
| 分页入参 | `pageNo`（从 1 开始）、`pageSize`（默认 10） |
| 分页返回 | `{ list, total, pageNo, pageSize, hasMore }` |
| 错误约定 | throw `ApiError`，字段与 HTTP 错误体一致：`{ error: { code, message, details } }`；码表见 `api/errors.js` |
| 登录态 | `uni.getStorageSync('token')`；HTTP 版通过 `Authorization: Bearer <token>` 传递 |
| 枚举来源 | 一律从 `@/api/index.js` 取（`ORDER_STATUS` / `BOOKING_TYPES` / `TIME_SLOTS` / `GUIDE_STATUS` / `ROLES`），页面不许自建映射表 |

## 1. RegionApi（区域字典，后台可维护）

| 方法 | HTTP | 入参 | 返回 |
|---|---|---|---|
| `getRegionList(params)` | `GET /regions` | `{ onlyWithAttractions = true }` | `RegionType[]` |

`RegionType`：`{ id, code, name, coverage, scene, sortOrder }`

> 默认只返回「启用且下有在售景点」的区域，避免首页出现点进去是空的标签（`山野度假线` 在补齐景点前即属此类）。

## 2. AttractionApi（景点）

| 方法 | HTTP | 入参 | 返回 |
|---|---|---|---|
| `getAttractionList(params)` | `GET /attractions` | `{ pageNo, pageSize, regionTypeId, regionTypeCode, keyword }` | 分页对象，`list: Attraction[]` |
| `getAttractionDetail(id)` | `GET /attractions/{id}` | `attractionId` | `Attraction` |

`Attraction`：`{ id, code, name, district, regionTypeId, regionTypeCode, regionTypeName, scene, coverUrl, summary, guideCount, sortOrder }`

> `guideCount` 在 mock 中按「已通过地陪 × 擅长该景点」实时计算；后端接入时对应 `attractions.guide_count` 冗余字段（由审核通过 / 解绑景点时维护）。

## 3. PackageApi（套餐 SKU）

| 方法 | HTTP | 入参 | 返回 |
|---|---|---|---|
| `getPackageList()` | `GET /packages` | 无 | `Package[]` |

`Package`：`{ packageSkuId, code, name, bookingType, bookingTypeLabel, durationDesc, price, priceMin, priceMax, includesNote, description }`

> `bookingType` 决定下单页控件（`BOOKING_TYPE_UI`）：`half-day` 显示上午/下午，`full-day` 隐藏时段，`hourly` 显示小时数。

## 4. GuideApi（地陪）

| 方法 | HTTP | 入参 | 返回 |
|---|---|---|---|
| `getGuideList(params)` | `GET /guides` | `{ pageNo, pageSize, attractionId, regionTypeId, regionTypeCode, bookingType, priceMin, priceMax, sort }` | 分页对象，`list: Guide[]` |
| `getGuideDetail(id)` | `GET /guides/{id}` | `guideId` | `Guide`（未通过审核返回 404） |
| `getGuideAvailableDates(id, params)` | `GET /guides/{id}/available-dates` | `{ days = 14, bookingType }` | `AvailableDate[]` |
| `getPendingGuides(params)` | `GET /admin/guides?status=0` | `{ pageNo, pageSize }` | 分页对象，`list: Guide[]` |
| `auditGuide(id, payload)` | `PATCH /admin/guides/{id}` | `{ status, auditedBy? }` | `Guide` |

`Guide`：`{ id, userId, nickname, avatarUrl, introduce, orderCount, status, statusLabel, regionTypeIds, regionTypes[{id,code,name}], attractionIds, bookingTypes, priceFrom, packages[] }`

`AvailableDate`：`{ appointDate, bookingTypes[], isAvailable }`

排序：`sort = 'priceAsc'` 按起价升序，默认按 `orderCount` 降序。

## 5. OrderApi（订单，四态）

| 方法 | HTTP | 入参 | 返回 | 状态变化 |
|---|---|---|---|---|
| `createOrder(payload)` | `POST /orders` | `{ guideId, attractionId, packageSkuId, appointDate, timeSlot?, hours?, peopleCount?, remark?, touristUserId? }` | `Order` | 新建 → `0 待确认` |
| `getMyOrders(params)` | `GET /orders` | `{ pageNo, pageSize, status }` | 分页对象 | — |
| `getGuideOrders(params)` | `GET /guides/me/orders` | `{ guideId?, scope: 'waiting'\|'inProgress'\|'all', pageNo, pageSize }` | 分页对象 + `counts` | — |
| `getAllOrders(params)` | `GET /admin/orders` | `{ pageNo, pageSize, status, appointDate }` | 分页对象 + `counts` | — |
| `getOrderDetail(id)` | `GET /orders/{id}` | `orderId` | `Order` | — |
| `acceptOrder(id)` | `PATCH /orders/{id}/accept` | `orderId` | `Order` | 写 `guideAcceptedAt`，**状态不变**（仍待平台确认） |
| `rejectOrder(id, payload)` | `PATCH /orders/{id}/reject` | `{ reason }` | `Order` | `0 → 3 已取消` |
| `confirmOrder(id, payload)` | `PATCH /orders/{id}/confirm` | `{ remark?, adminUserId? }` | `Order` | `0 → 1 已确认` |
| `completeOrder(id, payload)` | `PATCH /orders/{id}/complete` | `{ remark? }` | `Order` | `1 → 2 已完成` |
| `cancelOrder(id, payload)` | `PATCH /orders/{id}/cancel` | `{ reason }` | `Order` | `0/1 → 3 已取消` |

`Order`：`{ id, orderNo, touristUserId, guideId, attractionId, packageSkuId, bookingType, bookingTypeLabel, appointDate, timeSlot, timeSlotLabel, hours, peopleCount, remark, amount, status, statusLabel, statusKey, attractionName, packageName, guideNickname, guideAvatarUrl, waitingGuideAccept, inProgress, guideAcceptedAt, confirmedAt, finishedAt, cancelledAt, cancelReason, createdAt, updatedAt }`

### 5.1 状态与流转（唯一裁判：`api/constants.js`）

| status | key | 含义 |
|---|---|---|
| 0 | `pending-confirm` | 待确认（含「待地陪接单」与「待平台确认」两个子阶段，用 `guideAcceptedAt` 区分） |
| 1 | `confirmed` | 已确认（平台人工确认档期后） |
| 2 | `completed` | 已完成 |
| 3 | `cancelled` | 已取消 |

白名单：`0 → 1 / 3`，`1 → 2 / 3`，`2 / 3` 为终态。越权流转抛 `STATE_INVALID`（409）。

### 5.2 订单号

`CD + YYMMDD + 业务类型(A 半天 / B 全天 / C 专项·小时) + 4 位当日序号`，共 **13 位**，如 `CD260926A0001`。
生成：当日同类型取 `MAX(序号) + 1`；HTTP 版本必须补「唯一键撞号后重试」。
实现：`orderNoPrefix` / `buildOrderNo` / `nextOrderNo` / `parseOrderNoSeq`（`api/constants.js`）。

## 6. UserApi（用户与身份）

| 方法 | HTTP | 入参 | 返回 |
|---|---|---|---|
| `getCurrentUser()` | `GET /users/me` | 无 | `{ id, nickname, avatarUrl, phone, role, roleLabel, isAdmin }` |
| `wxLogin(params)` | `POST /auth/login` | `{ code, encryptedData?, iv? }` | `{ token, openid, userInfo }` |
| `saveUserInfo(info)` | `PATCH /users/me` | 用户字段 | `id` |
| `isAdmin()` | `GET /users/me` | 无 | `boolean` |
| `logout()` | `POST /auth/logout` | 无 | `true` |
| `switchRole(role)` | —（仅 mock） | `'tourist' \| 'guide' \| 'admin'` | 当前用户 |

> mock 默认身份是**管理员**（便于演示后台，与原代码 `isAdmin: true` 行为一致）；`switchMockRole` / `switchRole` 可切到游客或地陪视角。

## 7. 应用层完整性职责（数据库不使用外键，见 dev-005）

实现位置：`api/mock/index.js` 的 `createOrder` 与 `transit()`；HTTP 版本必须逐条对齐。

| 职责 | mock 实现 | HTTP 版本要求 |
|---|---|---|
| 写入前校验主体有效 | 校验景点上架、地陪已通过、套餐可售、地陪擅长该景点、档期可约、人数 1-9、时段/小时数匹配套餐类型 | 同左，后端在事务内校验 |
| 订单快照冗余 | 写入 `attractionName` / `packageName` / `guideNickname` / `guideAvatarUrl` | 同左（保证主体改名不回改历史订单） |
| 状态流转白名单 | `canTransit()`，越权抛 `STATE_INVALID` | 同左，服务端校验而非信任前端 |
| 订单号撞号 | 串行生成，天然不撞 | **必须**捕获唯一键冲突并重试（最多 3 次） |

## 8. 过渡适配层（临时，勿新用）

`ClerkApi` / `CategoryApi` / `AppointmentApi` 把新模型映射成陪玩时期的数据形状，只为让旧页面在迁移期间不白屏：

| 旧方法 | 映射到 |
|---|---|
| `CategoryApi.getCategoryList` | `RegionApi.getRegionList`（`_id` = 区域 code） |
| `ClerkApi.getClerkList` / `getClerkDetail` | `GuideApi`（`skills` = 擅长景点名，`city` = 区域名） |
| `ClerkApi.getPendingClerks` / `auditClerk` | `GuideApi.getPendingGuides` / `auditGuide` |
| `AppointmentApi.*` | `OrderApi.*`（状态做了「压缩」映射：新 0/1 → 旧 0 待服务） |

删除条件：`feat-006 ~ feat-012` 页面全部迁移完成（即 feature_list 中游客端 / 地陪端 / 管理端页面改完）。

## 9. 更新规则

- 新增或修改接口 → 改 `api/mock/index.js` 与 `api/http.js` 的 `ROUTES`，**同步本文件**，并在对应 feat 的设计文档里写清动机
- 枚举 / 状态 / 订单号规则变更 → 只改 `api/constants.js`，然后同步本文件与 `docx/database/数据库设计.md`
- 本文件与 `docx/database/数据库设计.md`、`api/http.js` 的 `ROUTES` 三者必须一致（字段名、路径、状态语义）
