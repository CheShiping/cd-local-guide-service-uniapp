## 1. 表清单（10 张）

| # | 表 | 用途 | MVP 角色 |
|---|---|---|---|
| 1 | `users` | 用户（游客/地陪/管理员共用，`role` 区分） | mock 预置 52 个（50 地陪 + 1 游客 + 1 管理员） |
| 2 | `region_types` | 区域类型字典（**后台可维护**，初始 7 类） | 首页顶部标签的数据来源；seed 初始化 |
| 3 | `attractions` | 景点（20 个，通过 `region_type_id` 归属区域） | mock 20 条，seed 初始化 |
| 4 | `guides` | 地陪（与 `users` 一对一） | mock 预置 50 个，含审核状态 |
| 5 | `guide_region_types` | 地陪擅长区域（多对多） | 卡片标签与筛选的数据来源 |
| 6 | `guide_attractions` | 地陪擅长景点（多对多） | **「先选景点 → 再选地陪」的匹配关系** |
| 7 | `package_skus` | 套餐 SKU（固定 3 个） | `booking_type` 决定下单页控件 |
| 8 | `guide_packages` | 地陪报价（地陪 × 套餐） | 列表/详情的价格来源 |
| 9 | `guide_available_dates` | 可约档期（一行 = 某地陪某天可接某类型） | 详情页「可约日期」 |
| 10 | `orders` | 订单（四态 + 13 位订单号） | 闭环核心 |

### 1.1 表数量的取舍过程

| 表 | 处理 | 理由 |
|---|---|---|
| `region_types` | **加回为字典表**（用户 2026-09-26 决策） | 区域要做成后台可维护的数据：名称、覆盖范围、排序、上下架都应是数据而不是代码里的 `ENUM`。一度按"固定 3 类枚举"精简掉，现按决策加回，并扩到 7 类 |
| `order_status_logs` | 删除 | MVP 只写不读；状态流转已由 `orders.status` + `confirmed_at` / `finished_at` / `cancelled_at` / `cancel_reason` 表达，订单号本身还能反查业务类型 |

最终 **10 张**。`order_status_logs` 的加回条件：需要统计拒单率、追溯谁改的状态时。

### 1.2 保留、不建议再合并的三处

| 想合并的 | 为什么不合并 |
|---|---|
| `guides` 并入 `users` | `users` 是登录表，合并后会塞入大量地陪专属可空列，职责混乱；1:1 用 `uk_guides_user_id` 表达即可 |
| `package_skus` 并入 `guide_packages` | 3 个套餐的名称/时长/说明是平台统一文案，合并后每行都要冗余一份，改文案要改 N 行；且它是 `mvp-scope.json` 里 `packages` 的单一来源 |
| `guide_region_types` 退化为 `guides` 上的标志列 | 区域已是可维护字典（会持续增加），标志列的方案每加一个区域就要 `ALTER TABLE`；关系表才能配合 `region_type_id` 自由扩展 |

### 1.3 区域字典是"可维护数据"，但 MVP 没有管理界面

`region_types` 表已经具备后台可维护的数据结构，但 **MVP 的 7 个页面里没有区域管理页**（页面清单见 `mvp-scope.json`，管理端只做订单管理与地陪审核）。因此 MVP 阶段：

- 区域数据由 `docx/database/seed.sql` 初始化，之后改名称/排序/上下架走运维 SQL
- 前台按「`status = 1` **且** 下有在售景点」过滤展示，避免出现点进去是空的标签
- 真正的「后台区域管理」界面列入 `futureUpgrades`（要做时只需加一个页面，表结构不用动）

## 2. 订单号规则（已定稿）

### 2.1 格式

```
CD + YYMMDD + 业务类型 + 4 位当日序号
```

| 字段 | 长度 | 含义 | 示例 |
|---|---|---|---|
| 平台前缀 | 2 | 固定 `CD`（Chengdu） | `CD` |
| 日期 | 6 | `YYMMDD`，下单当天 | `260926` |
| 业务类型 | 1 | `A` 半天陪游 / `B` 全天陪游 / `C` 专项·小时 | `A` |
| 当日序号 | 4 | 当日同类型从 `0001` 自增 | `0001` |

合计 **13 位**（`2 + 6 + 1 + 4`），示例 `CD260926A0001`。

> 注：需求里写的是"14 位"，按字段长度相加应为 13 位；`schema.sql` 按实际长度定义为 `CHAR(13)`。

### 2.2 业务类型映射

`package_skus.booking_type` → 订单号字母，订单号因此自带"是什么业务"的信息（可读、好查）：

| `booking_type` | 字母 | 说明 |
|---|---|---|
| `half-day` | `A` | 半天陪游（市区半日） |
| `full-day` | `B` | 全天陪游（市区全天） |
| `hourly` | `C` | 专项 / 小时加购（熊猫基地·都江堰专项等） |

### 2.3 序号生成

1. 取当日同类型最大序号：
   `SELECT MAX(CAST(SUBSTRING(order_no, 10, 4) AS UNSIGNED)) FROM orders WHERE order_no LIKE 'CD260926A%'`
   （前缀 `LIKE 'CD260926A%'` 是前缀匹配，可走 `uk_orders_order_no` 索引；不要写成 `%CD...`）
2. 序号 = MAX + 1，左补零到 4 位（从 `0001` 起）
3. 插入时依赖 `uk_orders_order_no` 唯一索引兜底：若并发撞号，捕获重复键并重试（建议最多 3 次）

**为什么不用单独的序列表**：MVP 单量小，前缀 + 唯一索引 + 重试已经够用，且不用多维护一张表；等出现持续性并发冲突再引入 `order_no_sequences`（`prefix_date + biz_type + last_seq` 行锁自增）或 Redis INCR。

### 2.4 容量与边界

- 单日单类型上限 `9999` 单（MVP 远达不到）；溢出时需扩展序号位数，届时订单号长度变化要同步 `CHAR(13)` 定义
- 订单号**不可变**：一旦生成即作为对外凭证，不随状态变化重写
- 序号只保证"当日同类型唯一"，跨类型/跨日不保证连续

## 3. 关键设计决策

### 3.1 预约类型由套餐决定，不在订单上重复选择

`package_skus.booking_type` 是 `half-day / full-day / hourly` 三选一，下单时复制到 `orders.booking_type`。与定稿原型下单页结构一致（原型 04 屏是「套餐行 + 时段分段」，没有独立的类型选择器），也是 `docs/mvp-scope.json` 的 `bookingTypeUi` 规则：

| 套餐类型 | 下单页控件 | `orders.time_slot` |
|---|---|---|
| `half-day` | 上午 / 下午分段控件 | `morning` / `afternoon` |
| `full-day` | 隐藏时段控件 | `none` |
| `hourly` | 小时数步进器 | `none`（用 `hours`） |

### 3.2 「先选景点再选地陪」靠 `guide_attractions`

`guide_attractions` 既是详情页的「擅长景点」标签，也是地陪列表的筛选依据（`idx_guide_attractions_attraction_id`）。

### 3.3 反范式冗余（规范允许，用于避免 N+1）

| 冗余字段 | 位置 | 原因 |
|---|---|---|
| `guide_count` | `attractions` | 列表卡片直接显示「N 位地陪可约」，避免每个景点去 count |
| `attraction_name` / `package_name` / `guide_nickname` / `guide_avatar_url` | `orders` | 订单列表要展示这几项，冗余后不 JOIN 三张表 |

维护方式：地陪审核通过 / 解绑景点时更新 `guide_count`；下单时快照写入订单冗余字段（订单是不可变历史，**即使景点改名也不回改**）。

### 3.4 状态与枚举

| 枚举 | 取值 |
|---|---|
| `users.role` | `tourist` / `guide` / `admin` |
| `package_skus.booking_type` / `guide_available_dates.booking_type` / `orders.booking_type` | `half-day` / `full-day` / `hourly` |
| `guides.status` | `0` 待审核 / `1` 已通过 / `2` 已拒绝 |
| `orders.status` | `0` 待确认 / `1` 已确认 / `2` 已完成 / `3` 已取消 |
| `orders.time_slot` | `morning` / `afternoon` / `none` |

`orders.status` 与现有代码的 3 态（0 待服务 / 1 已完成 / 2 已取消）**语义不兼容**，属 `feat-005` 的破坏性升级范围。

### 3.5 「待地陪接单」如何在四态下表达（feat-004 补充）

四态不足以区分「地陪还没接单」与「地陪已接单、等平台确认」，两者都处于 `status = 0 待确认`。因此增加：

| 字段 | 含义 |
|---|---|
| `orders.guide_accepted_at` | 为空 → 待地陪接单（地陪端接单页的数据来源）；有值 → 待平台确认 |

配套的调用语义（见 `docx/接口文档.md` 第 5 节）：

- `acceptOrder` **只写 `guide_accepted_at`，不改变 status**（平台还要人工确认档期）
- `rejectOrder` 才把状态推到 `3 已取消`
- 地陪端「待接单」= `status = 0 AND guide_accepted_at IS NULL`；「进行中」= `status = 1`

### 3.6 不使用外键约束（现阶段决策）

- 表之间只用 **id 关联 + 索引**，不加 `FOREIGN KEY`
- 目的：避免分库分表 / 高并发场景受约束，也避免本地开发与线上约束不一致
- 完整性改由**应用层**保证：
  1. 写入前校验主体存在（下单校验 `guide_id` / `attraction_id` / `package_sku_id` 有效且上架）
  2. 订单快照冗余关键名称与头像，即使主体后续变更，历史订单仍可读
  3. 关系表用 `UNIQUE INDEX` 防重复绑定（如 `uk_guide_attractions_guide_attraction`）
  4. 状态流转在应用层做白名单校验（只允许 0→1→2、0/1→3）
- `scripts/check-schema.mjs` 会**拦截任何 `FOREIGN KEY`**，防止被悄悄加回来

### 3.7 必备列按表语义分类

| 类别 | 表 | `created_at` | `updated_at` | `is_deleted` | 失效语义 |
|---|---|---|---|---|---|
| 业务表 | `users` `attractions` `guides` `package_skus` `orders` | 需要 | 需要 | **需要** | 软删除（历史订单仍要能追溯到主体） |
| 从属配置表 | `guide_packages` `guide_available_dates` | 需要 | 需要 | 不需要 | `enabled` / `is_available` 置 0 |
| 关系表 | `guide_region_types` `guide_attractions` | 需要 | 不需要 | 不需要 | 只增只删、永不更新 |

### 3.8 金额与图片

- 金额一律 `DECIMAL(10,2)`，禁止 `FLOAT/DOUBLE`（现有 `utils/index.js` 的 `formatPrice` 把入参当「分」，与元不一致，MVP 不使用它）
- 图片只存 URL（`cover_url` / `avatar_url`），前端不内置图片，字段为空时露出 `primary-container` 底色（`docs/mvp-scope.json` 的 `imageStrategy`）

## 5. 查询场景与索引理由

| 场景 | 查询 | 命中索引 |
|---|---|---|
| 首页区域标签 | `WHERE status = 1 ORDER BY sort_order` | `idx_region_types_status_sort_order` |
| 首页景点列表（按区域） | `WHERE region_type_id = ? AND status = 1 ORDER BY sort_order` | `idx_attractions_region_type_id_status` |
| 景点下的地陪列表 | `guide_attractions WHERE attraction_id = ?` 再取 `guides` | `idx_guide_attractions_attraction_id` |
| 按区域筛地陪 | `guide_region_types WHERE region_type_id = ?` | `idx_guide_region_types_region_type_id` |
| 地陪列表排序 | `WHERE status = 1 ORDER BY order_count DESC` | `idx_guides_status_order_count` |
| 我的订单（按状态分页） | `WHERE tourist_user_id = ? AND status = ? ORDER BY created_at DESC` | `idx_orders_tourist_user_id_status` |
| 接单页（地陪待接单） | `WHERE guide_id = ? AND status IN (0,1)` | `idx_orders_guide_id_status` |
| 后台按状态+日期筛选 | `WHERE status = ? AND appoint_date = ?` | `idx_orders_status_appoint_date` |
| 生成订单号取最大序号 | `WHERE order_no LIKE 'CD260926A%'` | `uk_orders_order_no`（前缀匹配） |
| 详情页可约日期 | `WHERE guide_id = ? AND appoint_date >= CURDATE()` | `uk_guide_available_dates_guide_date_type`（最左前缀） |

分页统一用 `pageNo / pageSize`（与现有 Api 层一致），大偏移量场景按规范改用 `WHERE id > ?`。

## 6. MVP 阶段的 mock 落地约定（feat-004）

1. `api/index.js` 里的 mock 对象字段名与第 4 节「接口/mock 字段」列**完全一致**，便于后端接入时零改动替换
2. mock 数据量（见 `docs/mvp-scope.json` 的 `mockScale`）：**7 区域 / 20 景点 / 3 套餐 / 50 地陪 / 52 用户**，订单覆盖 4 态
3. 字典与基础数据以 `docx/database/seed.sql` 为准（区域 7、套餐 3、景点 20），mock 不得自造不一致的区域或景点
4. 50 个地陪用**确定性生成**（固定 seed 的伪随机）而不是手写 50 条：覆盖 7 类区域（每人 1-3 个标签）、1-4 个擅长景点、1-3 个套餐报价（落在建议价区间内）、审核状态以「已通过」为主并保留少量待审/拒绝供后台审核演示；确定性保证每次启动数据一致，便于截图与回归
5. 分页验证：地陪 50 条（`pageSize = 10` → 5 页）、景点 20 条（→ 2 页），用于覆盖「加载更多」与 `hasMore` 边界
6. 关系数据用数组表达：`guide.attractionIds`、`guide.regionTypeIds`、`guide.packages[]`
7. 金额用整数「元」（如 `300`），与 `DECIMAL(10,2)` 的 300.00 等价，不引入小数运算
8. 订单号在 mock 里**按同一规则生成**（`CD + YYMMDD + 类型字母 + 序号`），不要用随机串；这样切后端时展示逻辑不用改
9. 景点区域归属以 `mvp-scope.json` 的 `regionAttractionMapping` 为准；`山野度假线` 当前无景点，前台按「启用且下有在售景点」过滤
10. mock 不实现 `order_status_logs`（表已取消），状态变化只改 `orders.status`
